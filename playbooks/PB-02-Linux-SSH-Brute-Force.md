# PB-02 — Linux SSH Brute Force Investigation

**Associated detection:** DET-01 — Linux SSH Brute Force — Repeated Failed Passwords  
**MITRE ATT&CK:** T1110.001 — Password Guessing

## Purpose

Provide a repeatable SOC investigation procedure for repeated SSH authentication failures against Linux systems. The core objective is to determine whether the activity remained an unsuccessful password-guessing attempt or resulted in successful access.

## Trigger

Triggered when DET-01 identifies repeated SSH authentication failures from the same source IP against the same target account.

## Required data

- `linux_secure` authentication telemetry
- `host`
- `src_ip`
- `src_port`
- `target_user`
- failure count
- `first_seen`
- `last_seen`
- `correlation_key`

## Initial triage

1. Identify the affected Linux host.
2. Identify the source IP.
3. Identify the targeted user.
4. Review failed-authentication count.
5. Review distinct source ports.
6. Record the `correlation_key`.
7. Determine first and last observed timestamps.
8. Determine whether the target is a valid account or an invalid user.

## Investigation procedure

### 1. Review failed authentication activity

```spl
index=soc_linux host="<HOST>" sourcetype=linux_secure "Failed password for"
| rex field=_raw "Failed password for (?:invalid user )?(?<target_user>\S+) from (?<src_ip>\S+) port (?<src_port>\d+) ssh2"
| search src_ip="<SOURCE_IP>"
| table _time host src_ip src_port target_user _raw
| sort _time
```

Confirm source IP, target user, source ports, failure count and observation window. Determine whether attempts are concentrated on one account or distributed across multiple accounts.

### 2. Review invalid-user activity

Search for `Invalid user` and `Failed password for invalid user` events. Record attempted usernames, SSH process/session identifiers, source IPs and source ports.

A high volume of invalid-user events may indicate username enumeration or automated password guessing.

### 3. Search for successful authentication

```spl
index=soc_linux host="<HOST>" sourcetype=linux_secure
("Accepted password for" OR "Accepted publickey for")
| rex field=_raw "Accepted (?<auth_method>password|publickey) for (?<target_user>\S+) from (?<src_ip>\S+) port (?<src_port>\d+)"
| search src_ip="<SOURCE_IP>"
| table _time host src_ip src_port target_user auth_method _raw
```

If successful authentication occurs after repeated failures, raise the investigation priority.

### 4. Review SSH session creation

Search the same source IP and time window for `session opened` and `session closed` events. Correlate SSH-related events using the available sshd process/session identifier where possible.

### 5. Build the authentication timeline

Construct a chronological sequence containing:

- `Invalid user`
- authentication failure
- `Failed password`
- `Accepted password`
- `Accepted publickey`
- `session opened`
- `session closed`
- connection reset

A compact outcome summary can be produced with:

```spl
index=soc_linux host="<HOST>" sourcetype=linux_secure
| search "<SOURCE_IP>"
| eval result=case(
    match(_raw,"Accepted password|Accepted publickey"),"SUCCESS",
    match(_raw,"Failed password"),"FAILED",
    match(_raw,"Invalid user"),"INVALID USER",
    match(_raw,"session opened"),"SESSION OPENED",
    true(),"OTHER"
)
| stats count by result
```

### 6. Assess post-authentication activity

If successful authentication or session creation is found, review the host for:

- shell execution;
- privilege escalation;
- new processes;
- account changes;
- persistence;
- scheduled tasks or cron jobs;
- suspicious file creation;
- network connections;
- lateral movement;
- commands associated with the authenticated user.

The absence of successful authentication should also be explicitly documented.

## Classification guidance

### True Positive — Successful Compromise

Password guessing resulted in successful unauthorized authentication or session creation.

### True Positive — Unsuccessful Brute Force

Repeated unauthorized authentication attempts occurred but did not result in successful access.

### Authorized Security Test

The activity was generated by an approved security test or laboratory simulation.

### Benign Positive

The activity matched the detection logic but investigation confirmed legitimate administrative behavior.

### False Positive

The detection logic incorrectly classified expected activity as suspicious.

## Severity guidance

Consider increasing severity when:

- authentication succeeds after repeated failures;
- an SSH session opens;
- a privileged account is targeted;
- multiple valid accounts are targeted;
- post-authentication suspicious activity appears;
- the source IP is known malicious;
- lateral movement follows authentication.

## Escalation criteria

Escalate when successful authentication follows repeated failures, a session opens, privileged or multiple valid accounts are targeted, post-authentication activity is detected, or the source is unauthorized/known malicious.

## Containment decision

For confirmed or strongly suspected unauthorized access, possible actions include source-IP blocking, account reset/disablement, terminating sessions, host isolation, credential rotation, preserving logs and reviewing `authorized_keys`.

For unsuccessful authorized laboratory activity, containment may not be required.

## Closure requirements

Document:

- affected Linux host;
- source IP;
- targeted user;
- failure count;
- invalid-user count;
- distinct source ports;
- successful-authentication findings;
- SSH-session findings;
- post-authentication findings;
- final classification;
- containment decision;
- analyst notes.

## Required evidence

- alert result;
- source IP;
- target account;
- failed-authentication count;
- first/last timestamps;
- successful-authentication search;
- SSH-session search;
- relevant raw authentication events;
- analyst classification.

## Metrics

Track brute-force alerts, unique source IPs, targeted accounts, successful compromises, unsuccessful brute-force cases, false/benign positives, escalations and average investigation time.

## Lesson from INC-02

The number of failed SSH authentication attempts alone is not sufficient to determine impact. Investigation must determine whether authentication succeeded, whether an SSH session was created and whether subsequent activity occurred on the target host.
